# Postgres dev dataset

Seed data for the `psql`, `psql13`, `psql14`, `psql15` and `psql17` services in
`docker-compose.yml`. It replaces the old Sakila dump with data shaped like what customers
actually connect Beekeeper Studio to: wide sparse tables, text and JSON values ranging from
empty to several megabytes, partitioned tables, and enums, composite types, domains, ranges
and binary data in many encodings.

Everything is generated by SQL at container start (`init.sh` runs the files in `seed/`), so
the repo stays small. A first start takes roughly 30-60 seconds and produces a ~500MB database.

| Service  | Version | Port | Database |
| -------- | ------- | ---- | -------- |
| `psql`   | 9.6     | 5432 | `saklia` |
| `psql13` | 13      | 5433 | `saklia` |
| `psql14` | 14      | 5436 | `saklia` |
| `psql15` | 15      | 5434 | `saklia` |
| `psql17` | 17      | 5437 | `saklia` |

User `postgres`, password `example`. The database keeps its old name so existing saved
connections, the Trino catalog and the e2e config keep working.

## Reloading

The postgres image only runs init scripts when the data volume is empty. To pick up changes
(or to move from the old Sakila data), remove the service's volume. The volume name is
prefixed with the compose project name, usually the checkout directory:

```bash
docker compose rm -sf psql15
docker volume rm beekeeper-studio_psql15
docker compose up -d --wait psql15
```

The services have a healthcheck that only passes once seeding has finished, so
`docker compose up --wait` returns when the data is ready.

## What's inside

### Wide tables

| Table                     | Columns | Notes |
| ------------------------- | ------: | ----- |
| `crm.salesforce_accounts` |    ~350 | Shape of a CRM object synced by an ETL tool: quarterly metric columns, per-product fields, five enrichment vendors, `_fivetran_*` columns. Mostly NULL. |
| `survey_responses`        |    ~470 | Survey export. Quoted mixed-case names (`"Q6_12"`, `"Duration (in seconds)"`), NULLs after the point a respondent stopped. |
| `customers`               |    ~150 | Grown a column at a time: flattened and composite addresses, consent flags, UTM fields, `custom_field_1..20` holding mixed junk. |
| `products`, `orders`      |   40-50 | Composite money and address types, arrays, ranges, `json` and `jsonb`. |

### Text and JSON of varying sizes

Sizes follow a long tail: about 5% empty, 65% under 500 bytes, 25% 1-20KB, 5% 20-200KB and
a few 1-2MB values.

- `support_tickets`: six text columns and seven JSON columns. Ticket 13 has a ~5MB
  description; ticket 42 has a ~7MB `source_payload`.
- `webhook_events`: rows 1-24 are JSON edge cases (top-level scalars and arrays, integers
  beyond 2^53, 5,000-key objects, 50,000-element arrays, nesting 100 levels deep, duplicate
  keys, unicode escapes). The rest look like real webhook traffic.
- `documents`: markdown and HTML bodies up to ~500KB and rich text editor JSON trees.
- `analytics.api_request_logs`: request and response bodies.

### Partitioning

| Table                        | Strategy |
| ---------------------------- | -------- |
| `analytics.events`           | RANGE by month, a `FROM (MINVALUE)` history partition, 3 empty future months, DEFAULT |
| `analytics.page_views`       | HASH, 8 partitions |
| `analytics.api_request_logs` | RANGE by day, pg_partman-style names (`api_request_logs_p20240131`) |
| `audit_log`                  | LIST by region, each sub-partitioned by RANGE of year (two levels) |
| `metrics_legacy`             | Old-style inheritance children with CHECK constraints and an insert trigger |

### Types

- Enums: `account_status`, `order_status`, `currency_code` and others. `workflow_stage` has
  labels with spaces, apostrophes, emoji and Cyrillic. `orders.status_history` is an enum array.
- Composite types: `postal_address`, `money_amount`, `geo_point`, `contact_method`, and
  `store_location`, which nests two of them. Arrays of composites appear in `users` and
  `products`.
- Domains (`email_address` over `citext`, `percentage`, `sha256_digest` over `bytea`), a
  custom range type (`floatrange`), built-in ranges, `hstore`, `ltree`, `inet`, `money`,
  `tsvector`, multi-dimensional arrays.
- Binary data:
  - `file_attachments`: real PNG, GIF, PDF, gzip and zip files; text files in 16 encodings
    with and without BOMs; random blobs up to ~5MB; an empty file; NULL content.
  - `inbound_emails`: bodies stored in the charset they arrived in (Shift_JIS, KOI8-R,
    UTF-16, ...) next to the base64 and RFC 2047 forms. Some rows declare `utf-8` but hold
    windows-1252 or iso-8859-1 bytes.
  - `integrations`: PGP-encrypted config, DER and PEM keys, base64 and hex secrets, a UUID
    stored as 16 raw bytes.

### Version differences

Files that need a newer server are skipped by `init.sh`:

| File                       | Needs | Adds |
| -------------------------- | ----- | ---- |
| `60_partitioning.sql`      | 11+   | All declarative partitioned tables (`metrics_legacy` exists everywhere) |
| `70_generated_columns.sql` | 12+   | Generated columns, `api_keys` with an identity key |
| `71_multiranges.sql`       | 14+   | Multirange columns |

### Extra databases

- `legacy_latin1`: `LATIN1` encoding with `bytea_output = escape`.
- `legacy_sql_ascii`: `SQL_ASCII` encoding. `contacts` holds UTF-8, Latin-1, Windows-1252 and
  Shift_JIS bytes side by side, so clients receive invalid UTF-8.

## Changing the data

Each file in `seed/` is plain SQL, loaded in the order listed in `init.sh`. Helper functions
for generating values live in the `seed` schema (see `00_setup.sql`) and are dropped at the
end. To add a file, put it in `seed/` and add a `bks_seed` (or `bks_seed_min_version`) line
to `init.sh`.
